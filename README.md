# Claude Fleet Console

Claude Code CLI を役割ごとに独立した Docker コンテナ上で実行し、その稼働状況をブラウザから可視化・操作するための構成です。単に複数コンテナを並べるだけでなく、**設計 → 実装 → レビュー → テスト**という開発の一連の流れを、それぞれ専用のコンテナに担当させ、**マスター（司令塔）役のコンテナが工程の完了ごとに成果物を読んで次に進めるかどうかを自動判断する**、というパイプライン運用ができます。

各コンテナは設定 (`~/.claude`) と作業ディレクトリを分離しつつ、ホストの `~/Project` を読み取り用の「vault」として、`~/Project/.fleet-handoff` を工程間で成果物をやり取りする書き込み可能な共有フォルダとして使います。

## 構成

- `Dockerfile` — `node:20-alpine` をベースに、Claude Code CLI (`@anthropic-ai/claude-code`) と `git` / `curl` / `bash` / `python3` / `go` などの開発ツールを導入したイメージ定義。非rootユーザー `claude` で実行されます。
- `docker-compose.yml` — 役割ごとのコンテナ定義（`claude-project-a` 〜 `d`、`claude-project-master`）と、管理UI の `manager` サービス。
- `manager/containers.config.json` — 各コンテナの表示名・権限モード・役割 (`role`) などをダッシュボードUI と紐づける設定ファイル。
- `manager/` — 管理ダッシュボード（Node.js + Express）。`http://127.0.0.1:4590` で待ち受けます。

### アーキテクチャ

```
ブラウザ ──5秒ポーリング + SSE──▶ manager ──/var/run/docker.sock──▶ claude-project-*
                                        └──/handoff（共有フォルダ）──▶ 各コンテナ
```

manager は各コンテナへ **`docker exec` 経由でのみ** アクセスします。稼働状況の取得・履歴の閲覧・タスクの投入をすべて `exec` に統一することで、manager に必要な追加マウントは `docker.sock` と `/handoff`（パイプラインの成果物受け渡し用）だけになります。

## この構成のメリット・デメリット

役割分業とマスターによる自動運転は、導入すれば必ず得になるものではありません。採用する前に、少なくとも次のトレードオフは把握しておいてください。

### メリット

- **役割分業による精度向上** — 設計・実装・レビュー・テストをそれぞれ専用のコンテナ・権限（permissionMode / allowedTools）・SKILL.md に分離できるため、「レビューのつもりでコードを直接直してしまう」ような役割の混線が起きにくい。
- **人間のボトルネックを解消できる** — マスターが工程完了ごとに自動で次を判断するため、都度人間が成果物を確認してボタンを押さなくても、チケットが最後まで（あるいは保留になるまで）流れる。
- **自動化の度合いを選べる** — マスター役を設定しなければ完全手動、設定すれば全自動、承認ゲートを併用すれば「危険な工程の手前だけ人間の確認を残す」半自動と、工程ごとに運用を選べる。
- **暴走に対する歯止めが複数ある** — 連続差し戻し・累計自動ホップ数の上限、全体一時停止スイッチ、承認ゲートという、独立した複数の安全装置が入っている。
- **文脈の混線を防ぐ設計** — チケット・工程ごとに Claude セッションを分離しているため、複数チケットを並行して流しても互いの文脈が混ざらない。
- **監査性** — 各工程の遷移が「誰が（人間かマスターか）・いつ・なぜ」判断したかとともに履歴に残り、チケット単位で使用量（コスト・トークン）も追える。
- **コンテナが隔離境界になる** — 各役割の失敗や暴走の影響は、基本的にはその役割のコンテナ（`/workspace`）に閉じる（`/handoff` と `/vault` は全コンテナ共有なので例外、デメリット参照）。

### デメリット

- **認証機構がない** — CSRF 対策（専用ヘッダ・`Sec-Fetch-Site` 検証）は入れているが本物の認証ではない。127.0.0.1 以外への公開や、信頼できないネットワーク・マルチユーザー環境での利用は想定していない。
- **フル自動運転はコストが読みにくい** — 1件のチケットが複数コンテナへ連鎖してタスクを送るため、人手で1件ずつ確認しながら進めるより早く・多く API 利用料を消費しうる。特にマスターの判断1回ごとにも実タスクが発生する。
- **マスターの判断の質は LLM 任せ** — プロンプトや SKILL.md で厳格化してはいるが、判断の正確さ・一貫性を完全には保証できない。成果物を精査せず楽観的に ADVANCE してしまう、あるいは逆に必要以上に HOLD/REJECT を連発する可能性がある。
- **`/handoff` が全チケット共有** — 書き込み可能な共有フォルダのため、あるチケットの成果物に紛れ込んだ内容（プロンプトインジェクション）が、理屈の上では別チケットの判断ファイルに影響しうる余地が残っている。
- **役割は1つにつき1コンテナが前提** — 同じ工程を複数コンテナへ並列に処理させる、といった水平スケールはできない。特定の役割が busy な間、その工程を待つチケットは詰まる。
- **チケット状態は単一ファイル・単一ロック** — `pipeline.json` 1ファイルに全チケットをまとめて保持し、変更操作は全チケット共通の1本のロックで直列化している。個人・小規模利用を前提とした設計で、大量のチケットを同時に高速処理する用途には向かない。
- **manager のメモリ・ローカルファイルに依存** — 使用量集計はメモリ上のみ（manager コンテナ再作成でリセット）、チケット等の状態は JSON ファイル保存であり、DB のような堅牢性・スケーラビリティは無い。
- **工程の構成が固定** — 設計 → 実装 → レビュー → テストの4工程＋マスターという構成はコード（`pipelineStore.js`）に直書きされており、UI から工程を増減・並び替えすることはできない。

## クイックスタート

```bash
docker compose build
docker compose up -d
```

各 Claude コンテナは `command: ["tail", "-f", "/dev/null"]` で常駐します。manager が `docker exec` で操作するには、コンテナが起動したままである必要があるためです。

ブラウザで開きます。

```
http://127.0.0.1:4590
```

起動直後は各コンテナが未ログイン状態です。[初回ログイン](#初回ログイン)を参照してください。

## ダッシュボードの基本操作

各プロジェクトはカードとして表示され、次の操作ができます。

| ボタン | できること |
| --- | --- |
| 起動 / 停止 / 再起動 | コンテナのライフサイクル操作 |
| 認証 | Claude Code へのログイン・ログアウト |
| 履歴 | 過去のセッションの閲覧、任意のセッションからの再開 |
| Skills | そのコンテナに登録されている `SKILL.md` の一覧表示・新規作成 |
| 差分 | `/workspace` の `git diff` を色付き表示（レビュー時に便利） |
| 設定 | permissionMode・allowedTools・役割 (role)・既定モデルなどの変更 |

カード下部の入力欄から、そのコンテナの Claude へ直接プロンプトを送ることもできます（パイプラインを使わない、単発のタスク実行）。実行中のコンテナへさらに投入すると自動でキューに積まれます。

## パイプライン機能（設計 → 実装 → レビュー → テスト）

複数のプロジェクトに役割を割り当て、1件の作業（チケット）を工程順に自動で受け渡していく機能です。

### 1. 各プロジェクトに役割を割り当てる

プロジェクトの「設定」ダイアログで「役割（パイプライン用）」を選びます。

| role | 担当する工程 | 標準的な権限設定 |
| --- | --- | --- |
| `design` | 設計 | `acceptEdits` + `Read/Grep/Glob/Write/Edit/WebSearch`（コード実行はさせない） |
| `implement` | 実装 | `bypassPermissions`（フル権限。コードを実際に変更する工程） |
| `review` | レビュー | `plan`（計画のみで実行はしない）+ `Read/Grep/Glob`（コードを直接編集させない） |
| `test` | テスト | `acceptEdits` + `Read/Grep/Glob/Bash/Write/Edit`（テストを実行できる） |
| `master` | 司令塔（後述） | `acceptEdits` + `Read/Grep/Glob/Write`（判断結果を書き出すだけ） |

「選択した役割のおすすめ設定を適用」ボタンを押すと、上表の permissionMode / allowedTools を一括で反映できます（保存を押すまで確定しません）。各役割につき1プロジェクトを想定しています。

`master` 役に設定したプロジェクトは、通常のカード一覧とは別に**画面上部の「司令塔（マスター）」枠に常時固定表示**されます。

実装工程のように「人間の確認なしに自動で進めてほしくない」工程には、設定ダイアログの「マスターの自動判断だけではこの工程へ進めない」にチェックを入れてください（[承認ゲート](#承認ゲート)を参照）。

### 2. チケットを作成する

ヘッダーの「パイプライン」ボタンからかんばんボード（設計・実装・レビュー・テスト・完了の5列）を開き、案件名を入力して「＋ 追加」します。新しいチケットは「設計」列に作成されます。

### 3. 工程に送る

チケットを選択し、「（現在の工程）へ(再)送信」を押すと、担当プロジェクトへタスクが投入されます。このとき、直前の工程の成果物への参照を含んだ指示文が自動で組み立てられます。

「次の工程へ」を押すと、次の工程へ進めつつタスクを送信します。「差し戻す」で、レビューやテストで問題が見つかった場合に任意の手前の工程へ戻せます。

### 4. 成果物の受け渡し（/handoff）

各工程は、成果物をチケットごとの共有フォルダ `/handoff/<チケットID>/` に書き出します。

| ファイル | 誰が書くか |
| --- | --- |
| `design.md` | 設計工程 |
| `implement.md`, `patch.diff` | 実装工程 |
| `review.md` | レビュー工程 |
| `test.md` | テスト工程 |

次の工程はこのフォルダを読んで作業を始めます。チケット詳細画面の「成果物」からいつでも内容を確認でき、`.diff` / `.patch` ファイルは差分ビューアと同じ色付き表示になります。

### 5. 司令塔（マスター）による自動運転

`master` 役のプロジェクトを設定しておくと、各工程のタスクが完了するたびに自動でマスターへ「成果物を読んで次にどうすべきか判断してください」という指示が送られます。マスターは次の3つのいずれかを判断し、理由とともに結果を書き出します。

- **ADVANCE** — 次の工程へ進めてよい
- **REJECT** — 問題があるので、指定した工程まで差し戻す
- **HOLD** — 判断がつかないため人間の確認が必要

manager はこの判断ファイルを読み、実際にチケットを進める／戻す処理を行います。これにより、一度チケットを流し始めると、人間がボタンを押さなくても最後まで（あるいは承認待ち・保留になるまで）自動で進みます。

マスターが判断した工程は履歴に「（マスター）」と表示され、人間が手動で操作した場合と区別できます。

`master` 役を設定していない場合は、これまでどおり人間がボタンを押して工程を進める手動運用になります（自動運転は完全にオプトインです）。

### 6. 承認ゲート

工程の設定で「マスターの自動判断だけではこの工程へ進めない」を有効にすると、マスターがその工程への ADVANCE/REJECT を判断しても実際には送信されず、「承認待ち」として記録されるだけになります。人間が成果物を確認し、手動で「次の工程へ」を押した場合だけ実際に実行されます（人間がボタンを押すこと自体が承認）。

破壊的な変更をしうる工程（既定では実装工程）には、この設定を有効にしておくことを推奨します。

### 7. 安全装置（暴走防止）

自動運転には次の歯止めが入っています。人間が手動で送信・進行・差し戻しを行うとリセットされます。

- **連続差し戻しの上限**（既定 3 回）— 同じところで往復し続けたら自動運転を一時停止
- **累計自動ホップ数の上限**（既定 12 回）— 差し戻しと前進を繰り返すパターンにも対応
- **全体一時停止スイッチ** — パイプライン画面から、すべてのチケットの自動運転をまとめて止められます

上限値は環境変数で調整できます（`docker-compose.yml` の `manager` サービスに追記）。

```yaml
environment:
  - PIPELINE_MAX_CONSECUTIVE_REJECTS=3
  - PIPELINE_MAX_AUTO_HOPS=12
```

一時停止中や承認待ちの状態は、チケット詳細画面に理由付きで表示されます。

### 8. セッションの分離

複数のチケットが同じ役割（同じコンテナ）を使い回しても、Claude のセッションはチケットごと・工程ごとに分離されています。あるチケットの設計工程の文脈が、別のチケットの設計工程に混ざることはありません（マスター自身の判断セッションも同様に分離されます）。

### 9. コストの確認

チケット詳細画面に、そのチケットが消費した累計コスト・トークン数・タスク数が表示されます（マスターの判断も含めて合算されます）。マスターに自動で複数工程を回させると、1件のチケットで複数コンテナへ実タスクが連鎖するため、その分の実使用量が発生する点に注意してください。

## Skills（SKILL.md）テンプレート

各コンテナの「Skills」ダイアログから、そのプロジェクト固有の `SKILL.md` を作成・上書きできます。「役割テンプレートから挿入」で、設計・実装・レビュー・テスト・マスターそれぞれの観点をまとめた叩き台を挿入できます（内容は保存前に自由に編集できます）。役割特化の精度を上げたい場合は、まずここを実際の運用に合わせて書き換えることをおすすめします。

## プロンプトテンプレート・差分表示

- ヘッダーの「テンプレート」から、コンテナ横断で使い回すプロンプトの雛形を登録できます。タスク投入フォームの「テンプレートを挿入」から使えます。
- 各カードの「差分」ボタンで、そのプロジェクトの `/workspace` の `git diff` を確認できます。

## 初回ログイン

Claude Code の認証はコンテナごとの名前付きボリュームに保存されるため、各コンテナで一度だけログインが必要です。ダッシュボードの「認証」ボタンから行えます。

1. カードの「認証」→「ログインを開始」を押すと、コンテナ内で `claude auth login` が起動します
2. 表示された認証 URL を開き、自分の Anthropic アカウントで認証します
3. 表示されたコードをダッシュボードの入力欄に貼り付けます

コードはコンテナ内の CLI の標準入力へ渡されるだけで、manager は保存もログ出力もしません。

CLI から行う場合は次のとおりです。

```bash
docker compose exec claude-project-a claude auth login
```

## 使用量・レート上限

ヘッダーに全コンテナ合計のコスト・トークン使用量を表示します。金額は CLI が返す `total_cost_usd` をそのまま合計したもので、manager が単価を計算し直すことはありません。累計はメモリ上にのみ保持しており、manager コンテナを再作成するとリセットされます。正式な請求額は Anthropic のコンソールを参照してください。

レート上限（5時間 / 週）はカード上部とヘッダーに表示します。Anthropic のアカウント使用状況 API を30秒間隔でポーリングしており、タスクを実行していなくても現在値が分かります。上限はアカウント単位で、同じアカウントでログインしたコンテナは同じ枠を食い合います。

## セキュリティ上の注意

このダッシュボードは**認証機構を持ちません**。以下を理解した上で利用してください。

- **`docker.sock` はホストの root 相当の権限です。** manager コンテナはホストの Docker を自由に操作できます。ポートは `127.0.0.1:4590` に限定して公開しており、これを `0.0.0.0` に変更してはいけません。
- **DNS リバインディング対策と CSRF 対策の両方を入れています。** `Host` ヘッダがループバック以外のリクエストは拒否し、さらに状態変更系リクエスト（GET 以外）には専用ヘッダと `Sec-Fetch-Site` の検証を必須にしています。単純な `<form>` からの偽装 POST や、別オリジンの Web ページからの `fetch` 偽装リクエストはブロックされます。とはいえ本物の認証ではないため、**信頼できないネットワークやマルチユーザー環境で 127.0.0.1 以外に公開することは想定していません**。
- **実装工程は既定で `bypassPermissions` です。** UI やパイプラインからプロンプトが投げられた瞬間、確認なしにコンテナ内でコマンド実行・ファイル編集が行われます。コンテナが唯一の隔離境界です。ツールを制限したい場合は `manager/containers.config.json` の各エントリに `allowedTools` を指定してください。

  ```json
  { "name": "claude-project-b", "allowedTools": ["Read", "Grep", "Glob"] }
  ```

- **`/vault` は全コンテナで共有された読み取り専用フォルダ、`/handoff` は全チケット共有の読み書き可能フォルダです。** `/vault` はホストの `~/Project` 配下を読み取れますが `:ro` のため書き込みはできません（**この `:ro` を外してはいけません**）。`/handoff` は書き込み可能なので、あるチケットの成果物に紛れ込んだ内容（プロンプトインジェクション）が、理屈の上では別チケットのファイルに影響しうる余地が残っています。外部の未信頼なコンテンツ（Web検索結果など）を扱う設計工程を使う場合は特に注意してください。
- **manager はレート上限の取得のため、各コンテナの OAuth access token を読み、Anthropic の API へ直接送信します。** token 自体はコンテナ内の `.credentials.json` から都度読み直すだけで、manager 側での保存・ログ出力・リフレッシュは行いません。
- **UI 操作中に同じコンテナへ手動で介入しないでください。** manager が `--resume` で書き込み中のセッションを `docker compose exec claude-project-a claude` で開くと競合する可能性があります。

## 新しいプロジェクトを追加する

ヘッダーの「＋ プロジェクト追加」から、プロジェクト名・ホスト側パス・役割・権限設定を指定して追加できます。保存後に「適用（docker compose up -d）」を押すと、`docker-compose.yml` と `manager/containers.config.json` の両方が更新され、コンテナが起動します。

手動で `docker-compose.yml` を編集する場合は、既存のサービス定義（`claude-project-a` など）を参考に、`/vault` と `/handoff` のマウントを含めてコピーしてください。

## 設定の永続化

各プロジェクトの Claude Code 設定・認証状態は名前付きボリューム（例: `claude-project-a-config`）に、パイプラインのチケット・テンプレート・自動運転の一時停止状態は `manager/` 配下の JSON ファイル（`pipeline.json`, `templates.json`, `autopilot.json`）に保存されます。設定をリセットしたい場合はボリュームを削除してください。

```bash
docker compose down
docker volume rm claude-containers_claude-project-a-config
docker compose up -d
```

## API 一覧

すべて `X-Fleet-Console: 1` ヘッダーを必須とします（GET を除く。[セキュリティ上の注意](#セキュリティ上の注意)参照）。

### コンテナ操作

| Method | Path | 概要 |
| --- | --- | --- |
| GET | `/api/containers` | 全コンテナの状態・使用量・レート上限 |
| GET | `/api/containers/usage/stream` | ヘッダー用のコスト・トークン・レート上限の SSE |
| POST | `/api/containers/:name/start` \| `/stop` \| `/restart` | ライフサイクル操作 |
| POST | `/api/containers/:name/tasks` | タスク投入（`{ prompt, newSession, model }`） |
| DELETE | `/api/containers/:name/task` | 実行中タスクの停止 |
| GET | `/api/containers/:name/task/stream` | 実行中タスクの SSE |
| GET | `/api/containers/:name/tasks/queue` | 実行待ちタスクの一覧 |
| DELETE | `/api/containers/:name/tasks/queue/:id` | キューから取り消し |
| GET | `/api/containers/:name/sessions` | セッション一覧 |
| GET | `/api/containers/:name/sessions/:id` | セッションの内容 |
| POST | `/api/containers/:name/sessions/:id/resume` | 次回投入で resume するセッションを切り替え |
| GET | `/api/containers/:name/diff` | `/workspace` の `git diff` |
| GET \| POST | `/api/containers/:name/skills` | SKILL.md の一覧取得・新規作成 |
| GET \| POST \| DELETE | `/api/containers/:name/auth...` | ログイン・ログアウト |
| DELETE | `/api/containers/usage` \| `/api/containers/:name/usage` | 使用量リセット |

### 設定・テンプレート

| Method | Path | 概要 |
| --- | --- | --- |
| GET \| POST \| PUT | `/api/config/projects` \| `/projects/:name` | プロジェクトの追加・編集 |
| GET | `/api/config/role-presets` | 役割ごとの推奨 permissionMode / allowedTools |
| POST | `/api/config/apply` | `docker compose up -d` を実行して反映 |
| GET \| POST \| DELETE | `/api/templates` | プロンプトテンプレート |
| GET | `/api/skill-templates` | 役割別 SKILL.md テンプレート |

### パイプライン

| Method | Path | 概要 |
| --- | --- | --- |
| GET | `/api/pipeline/stages` | 各工程の担当プロジェクト・承認要否 |
| GET | `/api/pipeline/master` | マスター役のプロジェクト |
| GET \| POST | `/api/pipeline/autopilot` | 全体の自動運転一時停止フラグ |
| GET \| POST | `/api/pipeline/tickets` | チケット一覧・作成 |
| GET \| DELETE | `/api/pipeline/tickets/:id` | チケットの取得・削除（削除時、関連する実行中タスクは停止される） |
| GET | `/api/pipeline/tickets/:id/usage` | チケット単位の累計使用量 |
| POST | `/api/pipeline/tickets/:id/send` | 現在の工程へ（再）送信 |
| POST | `/api/pipeline/tickets/:id/advance` | 次の工程へ進める |
| POST | `/api/pipeline/tickets/:id/reject` | 手前の工程へ差し戻す（`{ toStage, note }`） |
| GET | `/api/pipeline/tickets/:id/artifacts` \| `/artifacts/:filename` | 成果物（`/handoff`）の一覧・内容取得 |
